# Чек-ліст санітизації даних для роботи з AI

> Робочий документ команди QuitCode. Користуйтесь **щоразу** перед тим, як дати
> моделі бриф, лист клієнта, лог, вигрузку, скриншот чи експорт workflow.
> Приклад застосування: `docs/sanitized-brief.md`.

**Золоте правило:** документ іде в той інструмент, який дозволений для його
**найвищої** категорії. Один ключ у брифі робить увесь бриф 🔴.

---

## 1. Класифікація (світлофор)

| Категорія | Що сюди входить | Приклади | Куди можна |
|---|---|---|---|
| 🔴 Секрети | усе, що дає доступ | API-ключі, bot/PAT-токени, OAuth client secret, паролі, connection strings, n8n credentials, URL вебхуків, підписані URL (`?token=`, `?sig=`), cookies/сесії, приватні SSH-ключі | **нікуди**; лише out-of-band через env / secret manager |
| 🔴 PII | усе, що ідентифікує людину | ПІБ, email, телефон, адреса, месенджер-нік, ІПН/РНОКПП, паспорт, номер картки/IBAN, IP, фото, голос | **нікуди** в AI у сирому вигляді; лише замаскованим |
| 🔴 Продакшн-дані | реальні записи користувачів | вигрузки таблиць, дампи БД, логи/трейси з payload, HAR-файли, CSV з CRM | **нікуди**; замінити синтетикою того самого формату |
| 🟡 Внутрішня комерція | те, що шкодить агенції при витоку | ставки, собівартість, маржа, умови угод, конкуренти, дедлайни пропозицій | лише tier 🟡 (див. §6) — а краще прибрати, бо задачі це майже ніколи не потрібно |
| 🟡 Внутрішня логіка | те, що полегшує атаку чи розкриває клієнта | внутрішні хости й домени, ID баз/таблиць/проєктів, схеми БД, назви гілок і репо, внутрішні процеси, архітектура безпеки | лише tier 🟡 |
| 🟢 Постановка задачі | те, без чого модель не зрозуміє роботу | опис проблеми, кроки процесу, критерії приймання, обсяги й SLA без даних, публічні назви продуктів (Slack, Google Sheets, n8n) | будь-який дозволений інструмент |

**Сумнівний випадок → вища категорія.** Назва компанії клієнта — 🔴 (ідентифікує
клієнта й NDA), навіть якщо сама по собі «не секрет».

## 2. Що шукаємо (пошук перед відправкою)

Проганяємо **локально**, не через AI. Автоматизовано:
`bash .claude/scripts/sanitize-scan.sh <файл>` (або `/sanitize-check <файл>` у
Claude Code). Скрипт друкує **лише категорію й номери рядків**, а не значення, тож
навіть агент, що його запускає, секрету не бачить. Вихід `BLOCK` означає, що
документ не можна давати жодній моделі; `REVIEW` означає, що людина перевіряє,
чи збіги — плейсхолдери або синтетика. (Сам цей чек-ліст дає `BLOCK` на таблиці
нижче: у ній описано шаблони ключів. Це очікувано.)

| Що | Шаблон пошуку (regex, без урахування регістру) |
|---|---|
| Слова-маркери | `key\|token\|secret\|passw\|pwd\|credential\|bearer\|auth` |
| Відомі префікси ключів | `sk-\|xox[bpars]-\|ghp_\|github_pat_\|AKIA\|AIza\|eyJ` (JWT) |
| Токени виду `pat….…` (Airtable) та `name_live_…` | `pat[a-z0-9]{3,}\.[a-z0-9]{8,}` та `[a-z0-9]+_(live\|test)_[a-z0-9]{10,}` |
| Connection strings | `(postgres\|postgresql\|mysql\|mongodb(\+srv)?\|redis\|amqp)://` |
| Облікові дані в URL | `://[^/\s:]+:[^@\s]+@` |
| URL з токенами / вебхуки | `webhook\|hooks\.\|[?&](token\|key\|sig\|signature)=` |
| Email | `[\w.+-]+@[\w-]+\.[\w.]+` |
| Телефони UA (реальні коди операторів не починаються з 0) | `\+?380[\s(]*[1-9]\d` та `\b0[1-9]\d[\s-]?\d{3}` |
| Приховані інструкції для AI | `<!--\|SYSTEM\s*[/:]\|ignore (all\|previous)\|ігноруй` |
| IBAN / картки | `UA\d{27}` та `\b(\d{4}[\s-]?){4}\b` |
| Податкові коди | `\b\d{8}\b` (ЄДРПОУ), `\b\d{10}\b` (РНОКПП) |
| Адреси | `вул\.\|просп\.\|бульв\.\|кв\.\|оф\.\|м\. ` |
| Гроші й комерція | `\$\|₴\|грн\|маржа\|собівартість\|ставка\|/год` |

Плюс очима: таблиці «Доступи», підписи листів, вкладення, скриншоти (OCR бачить
усе), метадані `.docx`/`.pdf`, закоментовані рядки, base64 (закодований секрет —
все одно секрет).

**Приховані інструкції — теж предмет санітизації.** Клієнтський текст може
містити команди для AI: в HTML-коментарях, alt-тексті, тексті «білим по білому»
або як «обов'язкову вимогу ІТ-відділу» (прочитати `.env`, додати телеметрію).
Такий фрагмент не видаляємо мовчки: позначаємо `<SUSPECTED_INJECTION: короткий
опис>` і повідомляємо відповідальному, бо це сигнал про атаку на нашу
автоматизацію. Докладніше — `docs/injection-report.md`.

## 3. Як маскуємо

| Техніка | Що робить | Коли застосовувати | Приклад |
|---|---|---|---|
| **redaction** | прибирає значення повністю | дані не потрібні для задачі | `<REMOVED>`, `<PII_REDACTED>`, `<INTERNAL>` |
| **masking** | лишає форму, прибирає значення | важливий формат, не значення | `+380 (XX) XXX-XX-XX`, `****-1234`, `UA** **** 1234` |
| **synthetic / pseudonym** | замінює вигаданим | потрібні зв'язки між сутностями або реалістичні приклади | `[CLIENT_1]`, `[CONTACT_1]`, `orders@example.test`, `+380 (00) 000-00-01` |
| **out-of-band** | секрет узагалі не існує в тексті | **усі** секрети без винятку | `<SECRET_OUT_OF_BAND>` + ім'я env: `CRM_API_KEY` |
| **generalization** | зменшує точність | обсяги, дати, суми як орієнтир | «~400 заявок/тиждень», «суми 1–15 тис. ₴» |

Правила маскування:

- **Послідовність.** Одна сутність → один плейсхолдер у всьому документі
  (`[CLIENT_1]` скрізь, а не то `[CLIENT_1]`, то `[COMPANY]`). Інакше модель
  «побачить» двох різних клієнтів.
- **Таблиця відповідностей** `[CLIENT_1] → справжнє ім'я` зберігається лише
  локально / в CRM і **ніколи** не йде в промпт.
- **Синтетика — очевидно вигадана:** домени `*.example.test`, неіснуючий код
  оператора `00`, вулиця «Тестова». Правдоподібне «Ігор Мельник» може збігтися
  зі справжньою людиною.
- **Синтетика зберігає формат і крайові випадки,** які потрібні задачі
  (ФОП vs фізособа, `кв.`/`оф.`, пробіл-розділювач у сумах), — інакше модель
  напише валідацію під неіснуючий формат.
- **Роль лишаємо, особу прибираємо:** «керівник операційного відділу» корисно
  моделі, ПІБ — ні.
- **Не переборщити.** Критерії приймання, кроки процесу й обсяги лишаються
  дослівно. Якщо після маскування незрозуміло, що робити, — ви замаскували 🟢.

## 4. Креденшели інтеграцій (n8n, CRM, Slack, Airtable, БД)

1. **Ніколи** не вставляти значення в промпт, бриф, тікет, коміт, код, лог чи
   скриншот. У документі — лише `<SECRET_OUT_OF_BAND>` і **ім'я** змінної
   (`SLACK_BOT_TOKEN`), щоб розробник/агент знав, звідки його взяти.
2. Значення живуть лише в n8n credentials / secret manager / `.env` (у
   `.gitignore`). Агент отримує їх через env на етапі запуску й не має права
   читати `.env` чи виводити значення.
3. **URL вебхука = секрет.** Хто знає прод-URL, той може слати заявки. Експорт
   n8n workflow (JSON) містить URL вебхуків, ID і назви credentials, а в полях
   нод можуть лишитися захардкоджені токени — перевіряти перед тим, як ділитися.
4. **Least privilege** для того, що таки дається агенту: read-only репліка
   замість прод-БД, окремий токен з мінімальними scope, dev/staging-ключі
   замість live.
5. **Витік = ротація.** Якщо секрет потрапив у модель, чат, публічний репо чи
   історію git — вважаємо його скомпрометованим: **одразу** відкликати й видати
   новий, потім повідомити власника доступу. Видалення повідомлення чи коміту
   не допомагає.

## 5. Перед тим, як вставити в модель

- [ ] Визначив найвищу категорію документа (§1)
- [ ] Прогнав `bash .claude/scripts/sanitize-scan.sh <файл>` (шаблони з §2): немає `BLOCK`, усі `REVIEW` розібрані
- [ ] Приховані інструкції для AI (коментарі, «SYSTEM», «вимоги до підрядника») позначені й передані відповідальному
- [ ] Немає жодного справжнього ПІБ / телефону / email / адреси / месенджера
- [ ] Назва клієнта й внутрішні домени замінені плейсхолдерами
- [ ] Секрети й URL вебхуків → `<SECRET_OUT_OF_BAND>` + ім'я env, значень ніде немає
- [ ] Вигрузки замінені 2–3 синтетичними рядками того самого формату
- [ ] Комерція (ставки, маржа, собівартість, конкуренти) → `<INTERNAL>` або прибрана
- [ ] Вкладення, скриншоти й метадані перевірені або не додаються
- [ ] Перечитав результат очима моделі: задача й критерії приймання зрозумілі
- [ ] Обраний інструмент відповідає найвищій категорії, що **лишилась** (§6)
- [ ] Саму санітизацію робив **локально** (редактор / скрипт / локальна модель), а не через публічну модель

## 6. Інструмент під категорію

| Категорія (що лишилось після санітизації) | Інструмент / режим | Чому |
|---|---|---|
| 🟢 | будь-який затверджений командою AI-інструмент, включно зі звичайною підпискою з вимкненим використанням даних для навчання | даних, що шкодять при витоку, немає |
| 🟡 | лише бізнес/enterprise-план або API з комерційними умовами: контрактне no-train, DPA, контроль retention (в ідеалі zero data retention), SSO й адмін-керування доступами; для особливо чутливого — локальна модель | дані не йдуть у навчання, є юридичні зобов'язання й аудит |
| 🔴 у сирому вигляді | **не використовуємо AI**; спочатку санітизація (§3) → документ стає 🟢/🟡 | секрети й PII не повинні покидати контрольований периметр |
| 🔴 секрети при виконанні | лише env / n8n credentials / secret manager; агент бачить ім'я змінної, не значення | out-of-band за визначенням |
| Сама санітизація сирого документа | локально: редактор + пошук з §2, скрипт, або локальна модель (напр. через Ollama) | оригінал не повинен потрапити до зовнішнього провайдера ще до маскування |

Умови провайдерів змінюються — перед підключенням нового інструмента або плану
перевіряйте актуальні terms (training, retention, регіон зберігання) і фіксуйте
рішення тут.

### Який tier для 🟡 і чому

Для 🟡-даних (внутрішня логіка, назви систем, за потреби — комерція) обираємо
**бізнес/enterprise-підписку або API з комерційними умовами**, а не особисті
consumer-акаунти. Вирішальне — не «розумність» моделі, а контракт: no-train
зафіксоване в умовах, а не лише перемикачем у налаштуваннях, який будь-хто з
команди може забути; є DPA і контрольований строк зберігання; доступ іде через
корпоративні акаунти з SSO, тож при звільненні людини історія чатів не йде разом
з особистим акаунтом. Локальна модель дає найсильнішу гарантію (дані фізично не
покидають машину), але слабша за якістю й вимагає підтримки, тому її тримаємо для
вузьких випадків: попередня санітизація сирих документів і робота з комерцією,
яку не можна прибрати. І перш ніж обирати tier — перевіряємо, чи 🟡 взагалі
потрібне задачі: маржа чи собівартість для технічної автоматизації не потрібні
майже ніколи, простіше їх прибрати.

## 7. Якщо щось уже поїхало

1. Секрет → відкликати й перевипустити **негайно** (§4.5), потім розбиратись.
2. PII / продакшн-дані → повідомити відповідального за дані в агенції; видалити
   чат/файл у інструменті, якщо це можливо; зафіксувати, що, куди й коли пішло
   (для оцінки, чи потрібне повідомлення клієнта).
3. Додати в §2 шаблон пошуку або в §1 приклад, який пропустили, — щоб чек-ліст
   ловив це наступного разу.
